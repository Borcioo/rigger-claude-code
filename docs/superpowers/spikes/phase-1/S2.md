# S2: where plugin option values live

## Question

Where does Claude Code store a plugin's `userConfig` values, and can a rigger-core hook (or the
assembler) read rigger-talk's `reply_language`?

## CLI

- `claude --version`: `2.1.327 (Claude Code)`.
- `command -v claude`: `~/.local/bin/claude` (native Windows install).

## Setup

- Docs (plugins reference, "User configuration"): non-sensitive values are saved under
  `pluginConfigs` in the user's `settings.json`; `sensitive` values go to the platform's secure
  credential store; every option is exported to hooks as `CLAUDE_PLUGIN_OPTION_<KEY>`; values are set
  in the enable-time dialog or the `/config` panel.
- Non-interactive command, from `claude plugin --help`: `claude plugin configure <plugin@marketplace>
  --values-stdin` reads a JSON object of single-line strings (options left out keep their values);
  `--json` shows schema, inputs and which options are set. `claude plugin install` also prints
  "pass --config KEY=VALUE".
- `--plugin-dir` cannot take option values: `claude plugin configure rigger-talk` answers
  `No installed plugin has the id "rigger-talk"`. So the plugins were loaded through a directory
  marketplace: `<temp>/rigger-p1/S2/mkt` with `marketplace.json` (`name: rigger`) and copies of
  `plugins/rigger-talk` and `plugins/rigger-core` (no `.git`).
- Scratch hooks added to the copies: rigger-talk `printf 'S2-TALK-OPT=%s|%s|%s\n'` of the three
  `CLAUDE_PLUGIN_OPTION_*` values (`unset` when empty); rigger-core `printf 'S2-CORE-PROBE-RAN\n';
  env | grep '^CLAUDE_PLUGIN_OPTION_' | sed 's/^/S2-CORE-ENV: /'`. In the scope runs rigger-talk also
  runs the same `env | grep` line (positive control for the grep) and prints `S2_SCOPE_ENV`.
- Isolation as in S1 (stub behind `ANTHROPIC_BASE_URL`, fresh `CLAUDE_CONFIG_DIR`, home and cwd per run,
  inherited `CLAUDE_*`, `CLAUDECODE`, `ANTHROPIC_*`, `HARNESS_*`, `RIGGER_*` dropped, Remote Control
  off through `remoteControlAtStartup: false`, scratch `CLAUDE_CODE_PLUGIN_CACHE_DIR` and
  `HARNESS_LESSONS_INBOX`, `HARNESS_LESSONS_BATCH_OFF=1`). Canary passed in S1 on the same harness.
- Main run, in order: `claude plugin marketplace add <temp>/rigger-p1/S2/mkt`;
  `claude plugin install rigger-talk@rigger`; `claude plugin install rigger-core@rigger`;
  `echo '{"reply_language": "S2-LANG-<uuid>", "reply_lines": "7", "report_lines": ""}' |
  claude plugin configure rigger-talk@rigger --values-stdin`; then
  `claude -p s2probe-<uuid> --model haiku --output-format json --settings <run>/settings.json
  --debug-file <run>/debug-user.log`; then `rg -uu -l S2-LANG-<uuid>` over the config dir, the
  project dir (cwd) and the fake home.
- Scope runs: a fresh config each, same install, the value `S2-SCOPE-<scope>-<uuid>` set in exactly one
  place: `configure` (user), `<cwd>/.claude/settings.json` (project),
  `<cwd>/.claude/settings.local.json` (local), the `--settings` file (flag). The project, local and
  flag files also set `env.S2_SCOPE_ENV=read-<scope>` to prove the file was read.

## Control

Known answer: rigger-talk's own hook prints the value it was given. Observed in the main run:
`SessionStart:startup hook success: S2-TALK-OPT=S2-LANG-<uuid>|7|unset`. Passed on the first run.
`configure --json` afterwards listed `reply_language` and `reply_lines` as configured and
`report_lines` as unconfigured.

## Observed

- **Store:** `<config dir>/settings.json`:

  ```json
  "pluginConfigs": {
    "rigger-talk@rigger": {
      "options": { "reply_language": "S2-LANG-<uuid>", "reply_lines": 7 }
    }
  }
  ```

  Key path `pluginConfigs["<plugin>@<marketplace>"].options.<key>`. A `number` option given as the
  string `"7"` is stored as the JSON number `7`. An empty string is not stored at all: the key is left
  out and the hook sees the variable unset.
- `rg -uu -l` found the marker in two files only: `<config dir>/settings.json` and the session
  transcript under `<config dir>/projects/` (which holds the hook output). None in the project dir or
  the home.
- **Core probe:** `S2-CORE-PROBE-RAN` once, zero `S2-CORE-ENV:` lines in every run. In the same runs
  rigger-talk's identical `env | grep` printed `CLAUDE_PLUGIN_OPTION_REPLY_LANGUAGE=<value>`, so the
  variable exists only in the owning plugin's hook env. Only set options are exported.

| Scope | Where the value was set | Settings file read (`S2_SCOPE_ENV`) | rigger-talk hook saw the value |
|---|---|---|---|
| user | `claude plugin configure` → `<config dir>/settings.json` | n/a | yes |
| project | `<cwd>/.claude/settings.json` | yes | no (`unset`) |
| local | `<cwd>/.claude/settings.local.json` | yes | no (`unset`) |
| flag | `--settings <file>` | yes | yes |

Managed settings were not tested; the settings docs list `pluginConfigs` as "User or managed".

## Decision

**Branch A.** The values sit in a plain-text file the assembler can read: `pluginConfigs` in the user
`settings.json` of the config dir (`CLAUDE_CONFIG_DIR`, else `~/.claude`), key path
`pluginConfigs["<plugin>@<marketplace>"].options.<key>`; numbers as JSON numbers, empty strings
omitted. Scopes that hold it: user settings and the `--settings` flag (and, per the docs, managed
settings); project and local settings are ignored for it. The assembler reads it read-only (spec §9.6
default) and falls back to the `userConfig` defaults of `plugin.json`. The core probe did **not** see
`CLAUDE_PLUGIN_OPTION_*`, so the env var is not a source for the assembler. A `--settings` value
reaches the hook but is not on disk at a known path for the assembler; that gap is
Task 14's to note, not a branch change. `sensitive` options (none in Rigger today) would sit in the
credential store, outside this branch.
