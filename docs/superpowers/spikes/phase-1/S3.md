# S3: directory marketplace `installPath` lag, the root a hook sees, and version skew

## Question

For a directory marketplace: does the content under `installPath` lag the source after an edit,
which folder do hooks run from, and what exact `CLAUDE_PLUGIN_ROOT` string does a hook receive
(separators, drive-letter case, equal to `installPath` or to the source)? For a git-backed
marketplace (Step 6): can `rigger-rules` be updated without `rigger-core`, and can `dependencies`
carry a minimum version?

## CLI

- `claude --version`: `2.1.327 (Claude Code)`
- `command -v claude`: `<home>/.local/bin/claude.exe` (Windows 11, Git Bash `sh.exe` runs the hooks)
- Read right before the first run and again after the last run of this spike: unchanged.

## Setup

All runs use a fresh `CLAUDE_CONFIG_DIR` and a fake `HOME`/`USERPROFILE` per experiment. The child
env drops every `CLAUDE_*`, `ANTHROPIC_*`, `HARNESS_*`, `RIGGER_*` name plus `CLAUDECODE` and the
host OAuth switches, sets `ANTHROPIC_BASE_URL` to a local copy of
`plugins/rigger-rules/tests/stub_api.py` (or to a dead local port for plugin-management commands),
and sets `DISABLE_AUTOUPDATER=1` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`. Because
`CLAUDE_CODE_CHILD_SESSION` is cleared, Remote Control is switched off for the child; the debug log
shows `remote=false`, and an API-key stub login cannot start it. Canary before the first run: a
`claude -p` turn with a fresh word reached the stub (1 request), left the word in the scratch config
and in no file of the real config dir or the real `~/.claude.json`: PASS. Every `claude` call runs
through `Popen` with streamed stdout and a bounded timeout.

Steps 1–5 (directory marketplace), `<temp>/rigger-p1/S3/run1` and `run2`:

1. Copy the repository without `.git` to `<temp>/rigger-p1/S3/runN/repo`.
2. Append a scratch `SessionStart` group to the copy's `plugins/rigger-rules/hooks/hooks.json`
   with three handlers: `printf 'S3-ROOT=%s\n' "${CLAUDE_PLUGIN_ROOT}"`, the same value written
   with `printf '%s'` to a file (`subst.txt`), and `printenv CLAUDE_PLUGIN_ROOT` to a file
   (`env.txt`).
3. `claude plugin marketplace add <temp>/rigger-p1/S3/runN/repo`, then
   `claude plugin install rigger-rules@rigger` (it pulls `rigger-core` as a dependency).
4. Read `installed_plugins.json` and `known_marketplaces.json`.
5. Control (below), then append `S3-EDIT-<uuid>` to `repo/plugins/rigger-rules/rules/tests.md`.
6. `claude -p s3probe-<uuid> --model haiku --output-format json --debug-file <temp>/.../debug.log`
   against the stub; find the request by the probe word.
7. `claude plugin update rigger-rules@rigger` and read `installPath` again.

`run1` passed the repository path with an upper-case drive letter, `run2` with a lower-case drive
letter and lower-case folder names.

Step 6 (git-backed), `<temp>/rigger-p1/S3/skew1`: a second copy without `.git`, `git init`, one
commit. Three ways to add it as a marketplace, each in its own fresh config:

- `claude plugin marketplace add file:///<temp>/rigger-p1/S3/skew1/repo-git`
- `extraKnownMarketplaces.rigger.source` = `{"source": "git", "url": "file:///…"}` (and `"url"`)
  in the fresh config's `settings.json`, then `plugin install`
- a bare clone of it served on `127.0.0.1` by `git http-backend` (smart HTTP, a local folder only),
  `claude plugin marketplace add http://127.0.0.1:<port>/rigger.git`

On the third: install `rigger-rules@rigger` and `rigger-core@rigger`, append `S3-SKEW-<uuid>` to
`plugins/rigger-rules/rules/tests.md` and `plugins/rigger-core/rules/state-file.md`, commit, push
to the bare clone, `claude plugin marketplace update rigger`, then
`claude plugin update rigger-rules@rigger` alone. Read `installed_plugins.json` after each.

Dependency version floor, `<temp>/rigger-p1/S3/depver` and `depsem`: scratch plugin manifests
checked with `claude plugin validate`, then a scratch directory marketplace with `s3dep` and
`s3main` (`s3main` depends on `s3dep`), installed and started once against the stub with
`--output-format stream-json --verbose`, stopped at the init event.

## Control

- **Steps 1–5:** before any edit, `installPath/rules/tests.md` equals
  `repo/plugins/rigger-rules/rules/tests.md` byte for byte. Observed: equal (run1 and run2). The
  scratch `S3-ROOT` handler is in `installPath/hooks/hooks.json` too, so both copies carry it.
- **Step 6:** after `claude plugin update rigger-rules@rigger`, rigger-rules' `installPath` holds
  `S3-SKEW-<uuid>` (the update ran). Observed: yes, version moved `85be9b16363b` → `945ea046f764`.
- **Version floor:** a floor the dependency meets (`>=0.1.0` against `0.1.0`) loads both plugins.
  Observed: init `plugins` lists `s3main` and `s3dep`.

## Observed

Directory marketplace (Steps 1–5):

| Item | Value |
|---|---|
| `known_marketplaces.json` `rigger.source` | `{"source": "directory", "path": "<temp>/rigger-p1/S3/run1/repo"}` (stored with JSON-escaped backslashes and the drive letter as typed), `installLocation` the same path |
| `installPath` | `<temp>\rigger-p1\S3\run1\cfg\plugins\cache\rigger\rigger-rules\unknown` (version `unknown`: no `version` in `plugin.json`) |
| First request carries `S3-EDIT-<uuid>` | yes, once |
| `installPath/rules/tests.md` carries it | no (lags) |
| Hook commands in the debug log | `sh "<temp>\rigger-p1\S3\run1\repo\plugins\rigger-rules/rules/rules_start.sh" tests.md`: hooks run from the marketplace source, not from `installPath` |
| `S3-ROOT` (printed text, `subst.txt`, `env.txt`) | `<temp>/rigger-p1/S3/run1/repo/plugins/rigger-rules`, identical in all three; every separator `/`, upper-case drive letter as typed |
| Same file as source / as `installPath` | source: yes (`os.path.samefile`); `installPath`: no |
| run2 (path given with a lower-case drive and folder) | `S3-ROOT` = the same shape with the lower-case drive letter and lower-case folder names kept exactly as typed |
| After `claude plugin update rigger-rules@rigger` | `installPath/rules/tests.md` carries the edit ("refreshed from source") |

So `CLAUDE_PLUGIN_ROOT` = the marketplace `source.path` exactly as stored (drive-letter case as the
user typed it to `marketplace add`, which `known_marketplaces.json` keeps), joined with the
plugin's `source` without its `./`, with every `\` turned into `/`. The debug log displays the
substituted command with `\`, but the hook process receives `/` both through `${CLAUDE_PLUGIN_ROOT}`
in the command text and through the environment variable.

Git-backed marketplace (Step 6):

| Attempt | Result |
|---|---|
| `marketplace add file:///…` | refused: `Invalid marketplace source format. Try: owner/repo, https://..., or ./path` |
| `extraKnownMarketplaces` with `git` or `url` + `file://` | not materialised: `marketplace list` shows only the built-in directory; install says `Plugin "rigger-rules" not found in marketplace "rigger"` |
| dumb HTTP on `127.0.0.1` | treated as git, clone fails: `dumb http transport does not support shallow capabilities` |
| smart HTTP (`git http-backend`) on `127.0.0.1` | added; `known_marketplaces.json` source `{"source": "git", "url": "http://127.0.0.1:<port>/rigger.git"}` |

On the git-backed marketplace:

| After | rigger-rules `installPath` / marker | rigger-core `installPath` / marker |
|---|---|---|
| install | `cache\rigger\rigger-rules\85be9b16363b` / no | `cache\rigger\rigger-core\85be9b16363b` / no |
| `marketplace update rigger` | unchanged / no | unchanged / no |
| `plugin update rigger-rules@rigger` | `cache\rigger\rigger-rules\945ea046f764` / yes | `cache\rigger\rigger-core\85be9b16363b` / **no** |

With no `version` in `plugin.json`, a git install's version is the 12-character commit sha.
Updating rigger-rules alone left rigger-core on the old commit: the two run different versions.

Auto-update: `claude plugin update --help` and `claude plugin --help` say nothing about moving all
plugins of a marketplace at once; the online plugin documentation was not read (the spike ran with
no network beyond the stub and local git). Whether auto-update moves every plugin together stays
open.

Dependency version floor:

| `dependencies` entry | `plugin validate` | Install | Session load |
|---|---|---|---|
| `["rigger-core"]` | pass | – | – |
| `42` | fail: `expected array, received number` | – | – |
| `["rigger-core@>=0.4.0"]` | fail: `dependencies.0: Invalid input` | – | – |
| `{"rigger-core": ">=0.4.0"}` | fail: `expected array, received object` | – | – |
| `[{"name": "s3dep", "version": ">=0.1.0"}]`, dep `0.1.0` | pass | both installed | both loaded (control) |
| `[{"name": "s3dep", "version": ">=9.0.0"}]`, dep `0.1.0` | pass | both installed, no warning | `s3main` not loaded: `Requires "s3dep@s3m" >=9.0.0, installed 0.1.0`, error type `dependency-version-unsatisfied` |
| `[{"name": "s3dep", "version": ">=0.1.0"}]`, dep with no `version` | pass | both installed | `s3main` not loaded: `installed version unknown` |
| `[{"name": "s3dep", "bogusKey": "x"}]` | pass | both installed | both loaded (unknown keys are accepted, so `validate` passing proves nothing about a key) |

A floor exists and is enforced at load, not at install: the dependent plugin is dropped from the
session (not in the init `plugins` list), and the reason shows only in the debug log in this run.
No Rigger `plugin.json` or marketplace entry has a `version` today, so every Rigger install reports
`unknown` (directory) or a commit sha (git) and any floor would drop `rigger-rules`.

## Decision

- **`installPath` lags** for a directory marketplace (Steps 1–5 branch "If `installPath` lags"):
  Task 11 discovery reads a directory marketplace's module root from the marketplace `source.path`
  (`known_marketplaces.json`) joined with the plugin's `source` from that marketplace's
  `marketplace.json`, and prints that path in the root line. A `git` source keeps `installPath`.
- **Root line string form:** the exact form `CLAUDE_PLUGIN_ROOT` showed: the stored path with every
  `\` turned into `/`, drive-letter case unchanged (no case folding), the plugin's `source` joined
  without `./`. Comparisons between roots go through `samefile`/realpath, never string equality.
- **Step 6, branch "rigger-core stayed behind":** updating `rigger-rules` alone left `rigger-core`
  on its old version. A dependency floor exists (`{"name", "version"}` objects), but this
  repository cannot use it as it stands: its plugins carry no `version`, so a floor fails as
  `installed version unknown` and silently drops `rigger-rules`. Task 18 keeps the check handler in
  rigger-rules. Adopting the floor needs a `version` in every `plugin.json` first; that is a
  release decision, left to Task 22 and the owner. Open: whether auto-update moves all plugins of a
  marketplace together.
