# S4: which settings scopes enable a plugin

## Question

Which settings files' `enabledPlugins` maps decide whether an installed plugin loads, which scope
wins on a conflict, whether an install's `projectPath` limits where it loads, and how a
`--plugin-dir` plugin shows up — all read from the `plugins` array of the `stream-json` init event.

## CLI

- `claude --version`: `2.1.327 (Claude Code)`
- `command -v claude`: `<home>/.local/bin/claude.exe` (Windows 11)
- Read once before S3's first run, in the parent shell; every S4 debug log reports
  `cc_version=2.1.327`, so the CLI did not move.

## Setup

Isolation as in S3: a fresh `CLAUDE_CONFIG_DIR` and fake `HOME`/`USERPROFILE` per scenario, child
env without `CLAUDE_*`, `ANTHROPIC_*`, `HARNESS_*`, `RIGGER_*`, `ANTHROPIC_BASE_URL` set to a local
copy of `plugins/rigger-rules/tests/stub_api.py`, Remote Control off (`remote=false` in the debug
log); the same harness passed the S3 canary (stub reached, scratch config written, real config
untouched) earlier in the same session. Scratch: `<temp>/rigger-p1/S4/run1`.

1. Seven scratch plugins `s4-a` … `s4-g` (each only `.claude-plugin/plugin.json` with
   `"version": "1.0.0"`) in one directory marketplace `s4m`; an eighth, `s4-h`, in a separate
   folder and in no marketplace.
2. Base config: `claude plugin marketplace add <temp>/rigger-p1/S4/run1/mkt`,
   `claude plugin install s4-a@s4m` … `s4-f@s4m` (user scope), and `s4-g@s4m --scope project` run
   from `<temp>/rigger-p1/S4/run1/other-project`. Deviation from the plan's Step 1, which installs
   all seven in user scope: `s4-g` is installed in project scope only, so the test of
   `projectPath` is not masked by a user-scope install. Its `installed_plugins.json` entry
   is `{"scope": "project", "projectPath": "<temp>/rigger-p1/S4/run1/other-project", …}`, and the
   install wrote `{"enabledPlugins": {"s4-g@s4m": true}}` into that project's
   `.claude/settings.json`.
3. Each scenario copies the base config to a fresh config dir (rewriting the absolute paths in
   `plugins/*.json`), removes `enabledPlugins` from the user `settings.json` (keeping
   `extraKnownMarketplaces`), writes the scenario's maps, and runs from a fresh empty cwd that is
   not `other-project`:
   `claude -p s4probe-<uuid> --model haiku --output-format stream-json --verbose --debug-file <temp>/…/debug.log`,
   stopped at the `system`/`init` event. Scenario 8 adds `--plugin-dir <temp>/…/dirplug/s4-h` with
   `CLAUDE_CODE_PLUGIN_CACHE_DIR` and `HARNESS_LESSONS_INBOX` in scratch and
   `HARNESS_LESSONS_BATCH_OFF=1`.

"user" is `<config dir>/settings.json`, "user local" is `<config dir>/settings.local.json`,
"project" is `<cwd>/.claude/settings.json`, "project local" is `<cwd>/.claude/settings.local.json`.
Every run's init list also holds the CLI's three built-in plugins (`cc-plugin-agents-md`,
`cc-plugin-privacy`, `cc-plugin-plugin-authoring`); the table lists only `s4-*`.

## Control

Scenario 1 (user `s4-a: true`, nothing else) must list `s4-a` and no other `s4-*`. Observed:
`["s4-a"]`. Scenario 0 (no map anywhere) lists no `s4-*`, so installed plugins that no map
enables do not load.

## Observed

| Scenario | Setting | Init `plugins` (`s4-*`) |
|---|---|---|
| 0 | no `enabledPlugins` anywhere (installed only) | none |
| 1 | user `s4-a: true` | `s4-a` |
| 2 | user local `s4-b: true` | none |
| 3 | project `s4-c: true` | `s4-c` |
| 4 | project local `s4-d: true` | `s4-d` |
| 5 | user `s4-e: true` + project `s4-e: false` | none |
| 6 | project `s4-f: true` + project local `s4-f: false` | none |
| 7 | user `s4-g: true`, cwd is not `s4-g`'s `projectPath` | `s4-g` |
| 8 | `--plugin-dir` of `s4-h`, not installed | `s4-h` |
| 9 | project `s4-g: true`, cwd is not its `projectPath` | `s4-g` |
| 10 | user `s4-e: false` + project `s4-e: true` | `s4-e` |
| 11 | user `s4-b: false` + user local `s4-b: true` | none |
| 12 | project `s4-f: false` + project local `s4-f: true` | `s4-f` |
| 13 | user `s4-d: true` + project local `s4-d: false` | none |
| 14 | user `s4-d: false` + project local `s4-d: true` | `s4-d` |

Rows 0–11 ran in `run1`; rows 12–14 ran later in `run2` (a fresh base config built the same
way), with scenario 1 repeated there as its control (again `s4-a` only).

- **User `settings.local.json` is not read at all:** the debug log's
  `Watching for changes in setting files` line lists `<config dir>/settings.json` only, and
  scenarios 2 and 11 show no effect. In scenario 4 the same line lists the user `settings.json`
  and both project files.
- **Precedence:** project local over project over user, in both directions of each pair
  (scenarios 5 and 10, 6 and 12, 13 and 14): the more specific file's value wins, `true` or
  `false`.
- **`projectPath` is not honoured:** a project-scope install loads in any cwd whose settings
  enable it (scenarios 7 and 9).
- **Init entry shape:** `{"name": "s4-a", "path": "<temp>/…/mkt/plugins/s4-a", "source": "s4-a@s4m", "version":
  "1.0.0"}` (`path` stored with Windows backslashes). For a directory marketplace `path` is the marketplace source
  folder, not `installPath` (matches S3). A `--plugin-dir` plugin has `"source": "s4-h@inline"`
  and `path` the folder given.
- **Managed scope:** not probed. It lives in a system folder (the debug log shows the CLI looking
  for `managed-settings.json` under the program folder), and changing system settings is out of
  bounds for this spike.

## Decision

Branch "a scope behaves otherwise": spec §6.1 S4 lists user `settings.local.json` as a scope, but
the CLI does not read it; and a project-scope install's `projectPath` (which the spec does not
mention) does not limit where it loads. Task 11 discovery follows the observed table:

- read `enabledPlugins` from user `<config dir>/settings.json`, project `.claude/settings.json`
  and project `.claude/settings.local.json`, in that order, a later file overriding an earlier one
  key by key (managed settings: not probed, read with the highest precedence only if the spec's
  managed row is kept);
- do not read user `settings.local.json`;
- a plugin is enabled when the merged value is `true`; installed-but-unlisted is off;
- do not filter installs by `projectPath`;
- a `--plugin-dir` plugin is in the init list only (`source` ends in `@inline`), so it is compared
  through `RIGGER_MODULE_DIRS` as the spec says.

Every row of the table becomes a known-answer case in `test_discover.py`. The spec's S4 row is
corrected in the PR body.
