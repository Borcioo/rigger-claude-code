# E1: how an eval child learns its module roots

## Question

Does `claude plugin eval` pass the parent's environment (here `RIGGER_MODULE_DIRS`) to a case's child
session, and can a case's front matter set it through `env`?

## CLI

- `claude --version`: `2.1.327 (Claude Code)`.
- `command -v claude`: `~/.local/bin/claude` (native Windows install).
- `claude plugin eval --help` lists no per-case env option and no `--debug-file`
  (`error: unknown option '--debug-file'`), so the proof is the stub request text.

## Setup

- Harness and stub as in S1 (`<temp>/rigger-p1/E1/harness.py`, copy of `stub_api.py`); probe script
  `<temp>/rigger-p1/E1/e1.py`. Parent env: inherited `CLAUDE_*`, `CLAUDECODE`, `ANTHROPIC_*`,
  `HARNESS_*`, `RIGGER_*` dropped; fresh `CLAUDE_CONFIG_DIR` and home per run; `ANTHROPIC_BASE_URL`
  set to the stub. No settings file is passed to `claude plugin eval`; Remote Control cannot start
  because neither the parent nor the eval child (its own temp config) has an account login.
- Staged plugin `<temp>/rigger-p1/E1/staged/e1-probe`: `plugin.json` `{"name": "e1-probe"}`; one
  `SessionStart` `startup` hook printing `E1-ENV=${RIGGER_MODULE_DIRS:-unset}`, `E1-CWD=$(pwd)`,
  `E1-PROJECT-DIR`, `E1-ROOT=${CLAUDE_PLUGIN_ROOT}`, `E1-BASEURL-SET` and
  `E1-EVALVAR=${EVAL_E1_MARK:-unset}`; one case `evals/env-probe/prompt.md` (`plugins: ['../..']`,
  `runs: 1`, `max_turns: 1`, prompt with a unique `e1probe-<uuid>`) and one regex grader
  (`pattern: 'STUB-REPLY'`).
- Each run: `claude plugin eval <temp>/rigger-p1/E1/staged/e1-probe --no-publish --keep-temp
  --trust-plugin --ablation none --runs 1 --model haiku --output-dir <run>/results --json
  <run>/result.json --report <run>/report.html`, `Popen` with a 300 s bound. The request read is the
  stub request whose messages hold the probe word.
- Docs (plugin evals page): the child gets "a temporary home directory, working directory, and
  Claude Code configuration"; most of the shell environment is withheld, "only an allowlist and
  `EVAL_*` variables reach the run"; case `env` keys must match `EVAL_[A-Z0-9_]*`.

## Control

Known answer: the stub receives a request whose text holds `E1-ENV=`. Observed in the control run
(no `RIGGER_MODULE_DIRS` anywhere): one request with the probe word, holding
`SessionStart:startup hook success: E1-ENV=unset`; eval exit 0. The hook ran in the child. Passed on
the first run.

## Observed

| Run | Set where | Value set | Hook saw | Eval exit |
|---|---|---|---|---|
| control | nowhere | — | `E1-ENV=unset` | 0 |
| parent | parent env `RIGGER_MODULE_DIRS` | `E1-MARK-<uuid>` | `E1-ENV=unset` | 0 |
| parent | parent env `EVAL_E1_MARK` (same run) | `eval-E1-MARK-<uuid>` | `E1-EVALVAR=eval-E1-MARK-<uuid>` | 0 |
| case | case `env: {RIGGER_MODULE_DIRS: …}` | `E1-CASE-<uuid>` | no request; the run fails | 1 |
| case-eval | case `env: {EVAL_E1_MARK: …}` | `E1-CASE-<uuid>` | `E1-EVALVAR=E1-CASE-<uuid>` | 0 |

- The case run's `result.json` error: `case "env-probe" execution.env key "RIGGER_MODULE_DIRS" is not
  allowed — only EVAL_* keys can be set from case.yaml. Anything else must come from the operator's
  shell.` (the same rule applies to `prompt.md` front matter).
- `ANTHROPIC_BASE_URL` reached the child (`E1-BASEURL-SET=yes`, and the request reached the stub).
- Hook cwd: the run's empty temp working dir (`cwd` inside the run's temp `home` folder under `<temp>/claude-eval-<id>`; also
  `CLAUDE_PROJECT_DIR`), new per run. A relative `RIGGER_MODULE_DIRS` entry would resolve against
  that empty folder, not the staged plugins.
- `CLAUDE_PLUGIN_ROOT` in the child is the staged path itself (`<temp>/rigger-p1/E1/staged/e1-probe`),
  not a copy: a file next to a staged root is visible to the child's hooks. A rerun of the control
  with a second entry `plugins: ['../..', '../../deps/dep-probe']` showed the same for a staged
  dependency: `E1-DEP-ROOT=<temp>/rigger-p1/E1/staged/e1-probe/deps/dep-probe`.

## Decision

**Branch B (not inherited).** `RIGGER_MODULE_DIRS` from the parent env does not reach the eval child,
and a case cannot set it (only `EVAL_*` keys are allowed, and a case file could hold relative roots
only, which would resolve against an empty temp cwd). `eval_stage.py` writes
`<staged rigger-core>/.rigger-module-dirs`, one staged root per line, and discovery reads that file
next to its own root when present. A shipped install never holds the file. Observed fact for the
coordinator: parent `EVAL_*` variables do pass through.
