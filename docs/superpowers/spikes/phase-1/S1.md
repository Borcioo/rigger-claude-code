# S1: parallel part handlers all reach the context

## Question

Do 6 handlers of one `SessionStart` group each reach the first model request exactly once, as their
own `SessionStart:startup hook success:` block, in which order, and does each arrive whole at about
9,000 bytes per handler?

## CLI

- `claude --version`: `2.1.327 (Claude Code)`, read right before the first run.
- `command -v claude`: `~/.local/bin/claude` (native Windows install, hooks run through Git Bash `sh`).

## Setup

- Harness: `<temp>/rigger-p1/S1/harness.py` (pattern of `plugins/rigger-rules/tests/test_reinject.py`
  `claude_turn`/`copies`) and a copy of `plugins/rigger-rules/tests/stub_api.py`, behind
  `ANTHROPIC_BASE_URL` (stub, no model, no cost). Probe script `<temp>/rigger-p1/S1/s1.py`.
- Every run gets a fresh `CLAUDE_CONFIG_DIR`, `HOME`/`USERPROFILE`, cwd and scratch dirs under
  `<temp>/rigger-p1/S1/runs/<name>/`. The child env drops every inherited `CLAUDE_*`, `CLAUDECODE`,
  `ANTHROPIC_*`, `HARNESS_*` and `RIGGER_*`, then sets `CLAUDE_CONFIG_DIR`, `ANTHROPIC_BASE_URL`,
  `ANTHROPIC_API_KEY=stub-key`, `CLAUDE_CODE_PLUGIN_CACHE_DIR` and `HARNESS_LESSONS_INBOX` (scratch),
  `HARNESS_LESSONS_BATCH_OFF=1`, `DISABLE_AUTOUPDATER=1` and `SPIKE_RUN=<uuid>`.
  `CLAUDE_CODE_CHILD_SESSION` is cleared too, so Remote Control is disabled through
  `--settings` (`"remoteControlAtStartup": false`); the child also has no account login.
  The settings file also sets `claudeMdExcludes: ["**/CLAUDE.md"]`.
- Isolation canary before the first run: `claude -p canary-<uuid>` under a scratch config. The word
  reached the stub once, sat in 1 file of the scratch config, and `rg -uu -l` over the real config dir
  found nothing (exit 1). Pass.
- Probe plugin `<temp>/rigger-p1/S1/plugin`: `plugin.json` `{"name": "spike-parts"}`; `hooks.json`
  one `SessionStart` group, matcher `startup|clear|compact`, 6 handlers, handler `i` =
  `printf 'S1-PART-%s-i\n' "$SPIKE_RUN"`.
- Each session: `claude -p s1probe-<uuid> --plugin-dir <temp>/rigger-p1/S1/plugin --model haiku
  --output-format json --settings <run>/settings.json --debug-file <run>/debug-<name>.log`, run with
  `Popen`, stdout streamed to a file, 120 s bound. The request read is the one stub request whose
  messages hold the probe word.
- Size run: each handler runs `sh "${CLAUDE_PLUGIN_ROOT}/hooks/big.sh" <i> 8900`, which prints
  `S1-PART-<run>-<i>`, 89 filler lines of 99 `x` plus LF (8,900 bytes), then `S1-END-<run>-<i>`.

## Control

Known answer: a seventh handler `printf 'S1-CONTROL-%s\n' "$SPIKE_RUN"` in a second group appears
exactly once in the probe request. Observed: `S1-CONTROL-<run>` count 1, all 6 part markers count 1,
7 `Hooks: SessionStart:startup` lines in the debug log. Control passed on the first run.

## Observed

| Run | Markers (count each) | Own blocks | Debug `Hooks: SessionStart:startup` | Order in the request |
|---|---|---|---|---|
| control | 1,1,1,1,1,1 (+ control 1) | 6 | 7 | 1 2 5 3 4 6 |
| run-1 | 1,1,1,1,1,1 | 6 | 6 | 1 2 4 5 6 3 |
| run-2 | 1,1,1,1,1,1 | 6 | 6 | 2 1 3 6 5 4 |
| run-3 | 1,1,1,1,1,1 | 6 | 6 | 1 2 3 5 4 6 |
| run-4 | 1,1,1,1,1,1 | 6 | 6 | 1 2 4 6 3 5 |
| run-5 | 1,1,1,1,1,1 | 6 | 6 | 2 1 4 3 5 6 |
| size 8900 | 1,1,1,1,1,1; end lines 1,1,1,1,1,1 | 6 | 6 | 2 1 5 6 4 3 |

- "Own blocks" counts lines `SessionStart:startup hook success: S1-PART-<run>-<i>`: each handler
  arrives as its own block.
- The request order equals the order of the handlers' `finished with status 0` lines in the debug log
  (checked in run-1: 1 2 4 5 6 3 in both): handlers run in parallel and their texts are added in
  completion order, not `hooks.json` order.
- Size run: between each marker and its end line the request holds exactly 8,900 bytes and 89 filler
  lines, so no part was cut or persisted to a file. The "saved to / too large" phrases in the request
  occur equally often (2) in a plain run, so they come from the CLI's own prompt, not from a hook.

## Decision

Pass: all 6 markers exactly once in each of the 5 runs, and all 6 end lines whole in the size run.
K handlers stay, per D3 and D12. **Order varies** (0 of 5 runs in `hooks.json` order; the order is
handler completion order). Per D3 this changes no code: every part starts with the `Plugin root:` line of the first module it carries and repeats it when the module changes, so a part is self-contained whatever the order.
