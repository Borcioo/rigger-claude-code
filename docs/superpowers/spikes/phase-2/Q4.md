# Q4: starting an external program with no shell

## Question

Can `slot_run.py` (Task 14) start an external reviewer with `subprocess.Popen(argv, shell=False)`
safely and within bounds, on Windows and Linux? Specifically:

- Does a bare program name ever run a file planted in the repository?
- Does the lookup Task 14 plans ever return such a file?
- Does the tree kill of `scripts/run_tests.py` stop a grandchild?
- Does a console bound stop a child that floods its output?
- What does a `.cmd` shim do to arguments?

No `claude` run.

## Setup

- `q4.py` starts every child with `subprocess.Popen(argv, shell=False, env=<stripped>,
  cwd=<explicit>)`. The stripped environment is `os.environ` without `CLAUDE_*`, `HARNESS_*` and
  `RIGGER_MODULE_DIRS`.
- On POSIX every child gets `start_new_session=True`, as `run_tests.py` does.
- The child is a Python script that writes its argv as JSON to a file.
- The tree kill is `scripts/run_tests.py` `kill_tree`, copied as it is.
- The folder `repo` stands for the cloned repository.
- On Windows the planted program is a copy of `<system folder>/hostname.exe` named
  `reviewer-cli.exe`. A run is recognised by the host name it prints. On Linux it is an executable
  script that prints a marker.
- On Windows the `PATH` given is the system folder, which holds no `reviewer-cli`. On Linux it is
  `/usr/sbin`.
- On Windows, `NoDefaultCurrentDirectoryInExePath` is set to `1` once and removed once, in the
  process's own environment, and restored in `finally`.
- Linux ran from the distro's own `/tmp`, not from `/mnt`.
- Scratch: `<temp>/rigger-p2/q/Q4/`.

## Control (Step 2)

## Case 2: the planned lookup

This is Task 14's `resolve_program`, bare-name branch:

- Walk the `PATH` entries in order.
- Skip an entry that is empty, not absolute (on Windows, one with no drive), or whose real path lies
  inside the repository or the working directory.
- The candidates are `<name>.exe` and `<name>.com` on Windows, and `<name>` with the execute bit
  elsewhere.
- The real path of the result must lie outside both.

The working directory is the repository. The rows ran with the setting `1` and removed on both
Windows Pythons, and on Linux.

| `PATH` | `reviewer-cli` | Control (`hostname` / `nologin`) |
|---|---|---|
| system folder only | nothing | found in the system folder |
| system folder + empty entry | nothing | found |
| system folder + `.` | nothing | found |
| system folder + `sub` (relative, holds a copy) | nothing | found |
| system folder + the repository root, absolute | nothing | found |
| system folder + a repository subfolder holding a copy, absolute | nothing | found |
| the repository root, then a folder outside it that holds a copy | the copy outside the repository | not on this `PATH` |

The result is the same in every row on 3.12.10, 3.11.9 and 3.10.12, under both settings. The
planned lookup never returned a file inside the repository. It still finds a real program, and a
copy outside the repository that comes after a skipped entry.

## Case 3: tree kill

A child starts a grandchild that sleeps 60 s and writes its pid. Then the child is stopped with
`kill_tree`.

| Python | Grandchild alive before | Grandchild alive after | Child return code | Seconds, start to check (includes a 0.5 s wait) |
|---|---|---|---|---|
| 3.12.10 Windows | yes | **no** | 1 | 1.29 |
| 3.11.9 Windows | yes | **no** | 1 | 1.27 |
| 3.10.12 Linux | yes | **no** | -9 | 0.55 |

On Windows "alive" was read from `tasklist /FI "PID eq <pid>"`. On Linux it was read from
`/proc/<pid>/stat`, where a zombie counts as gone.

## Case 4: output bound (limit 1 MB = 1,048,576 bytes)

The writer prints 64 KB chunks. "Fast" means 800 chunks (50 MB) with no pause, "paced" means a 10 ms
pause per chunk, and "never-ending" means no end. In the file rows, stdout goes to a temp file whose
size is polled every 20 ms, and `kill_tree` runs once the file passes the limit; this is the plan's
form. In the pipe rows, stdout is a pipe that a thread reads, counting bytes; it stops reading and
runs `kill_tree` once the count passes the limit.

| Python | Sink, writer | Size when the bound fired | Bytes after the kill (1 s later) | Return code |
|---|---|---|---|---|
| 3.12.10 Windows | file, fast | 44,957,696 | **52,428,800** (all of it) | **0**: it finished before the kill landed |
| 3.12.10 Windows | file, paced | 1,179,648 | 2,752,512 | 1 |
| 3.12.10 Windows | file, never-ending | 43,253,760 | **809,107,456** | 1 |
| 3.12.10 Windows | pipe, fast | (read) 1,114,112 | | 1 |
| 3.12.10 Windows | pipe, never-ending | (read) 1,114,112 | | 1 |
| 3.11.9 Windows | file, fast | 6,750,208 | **52,428,800** (all of it) | **0** |
| 3.11.9 Windows | file, paced | 1,114,112 | 2,818,048 | 1 |
| 3.11.9 Windows | file, never-ending | 4,587,520 | **821,362,688** | 1 |
| 3.11.9 Windows | pipe, fast | (read) 1,114,112 | | 1 |
| 3.11.9 Windows | pipe, never-ending | (read) 1,114,112 | | 1 |
| 3.10.12 Linux | file, fast | 5,046,272 | 5,177,344 | -9 |
| 3.10.12 Linux | file, paced | 1,179,648 | 1,179,648 | -9 |
| 3.10.12 Linux | file, never-ending | 1,179,648 | 1,245,184 | -9 |
| 3.10.12 Linux | pipe, fast | (read) 1,114,112 | | -9 |
| 3.10.12 Linux | pipe, never-ending | (read) 1,114,112 | | -9 |

The process tree is stopped in every row, and the file does not grow after the kill. With a file
sink on Windows, though, the output is not bounded:

- A fast writer finishes its whole 50 MB before `taskkill` lands, and exits 0.
- A never-ending writer reaches about 800 MB between the bound firing and the kill completing. The
  kill alone was not timed.

With a pipe, the reader holds the child at the limit plus one chunk (1,114,112 bytes read) on every
Python and both systems. The child blocks on the full pipe while the kill runs.

## Case 5: a `.cmd` shim (Windows only; for the release notes)

The shim has the shape npm writes (`SET dp0=%~dp0`, then `"<python>" "%dp0%\child.py" %*`). It was
started with `Popen([shim] + the five control strings, shell=False)`.

| Python | Arrived | Return code | stderr |
|---|---|---|---|
| 3.12.10 | `["a b", "x"]` | 1 | `'y' is not recognized as an internal or external command, operable program or batch file.` |
| 3.11.9 | `["a b", "x"]` | 1 | the same |

`cmd.exe` split `x&y` at the `&` and tried to run `y` as a second command. A batch file is a shell
even with `shell=False`. This is ruling 9's reason, measured.

## Answer

- **Lookup:** a bare name given to the operating system runs a file planted in the repository. On
  Windows this happens when the calling process's working directory is the repository and the
  setting is absent. On Linux it happens with an empty or `.` `PATH` entry. `shutil.which` on 3.11
  ignores the setting. The planned lookup returns nothing in every case, under every setting.
- **Tree kill:** the grandchild is gone after `kill_tree` on every Python and both systems.
- **Output bound:** the file sink polled for size does not bound the output on Windows. The bound
  fires, but a fast writer completes its 50 MB and a never-ending one reaches about 800 MB before the
  kill completes. A pipe read with a byte count stops at 1,114,112 bytes everywhere.
- **`.cmd` shim:** it splits an argument at `&` and runs the rest as a command.

## Decision

- **Case 1 runs the planted file under some setting, and case 2 returns nothing under every
  setting:** Task 14 uses the planned lookup as written.
- **The grandchild survives:** no. It is gone in every row.
- **The output bound does not stop the child:** for the file sink on Windows, this branch holds.
  The tree is stopped, but the output is not bounded, and that was what the bound was for. Per the
  plan this is **`BLOCKED`** for Task 14 Step 4's sentence "Console output goes to a temp file, not a
  pipe, and the wait loop polls its size". The output above is the evidence.
  - The measured alternative is the pipe rows: a pipe read in a thread that counts bytes and stops
    past `CONSOLE_CAP`. It held at 1,114,112 bytes on both systems and every Python.
  - Choosing the sink is the coordinator's ruling, not the spike's. Task 14's
    `test_output_over_the_cap_refuses` (`flood`, cap 10,000) should assert a size bound on what was
    kept, not only the refusal line.

## Departures

- **The planted Windows program** is a copy of `hostname.exe`, not `whoami.exe`. Its output (the
  host name) identifies a run without arguments.
- **Case 1 has extra rows:** the parent's working directory both in the repository and elsewhere.
  Task 14's test sets it to the repository root.
- **Case 2 has extra rows:** a relative folder, the repository root and a subfolder as absolute
  entries, and a copy outside the repository after a skipped entry. Each row has a control that
  must be found.
- **Case 4 has extra rows:** a paced writer, a never-ending writer, and the pipe sink. Every row
  records its return code.
