# Q3: what a model-started shell command can see, and whether a stub can script one

## Question

When the model runs a command through a shell tool:

- What does the process see: its working directory, its environment names, the session id,
  `CLAUDE_CONFIG_DIR`?
- Does the argv of the `## Slots` line (D36) arrive whole?
- Can a stub API make a `claude -p` session run such a command, and with which permission form?
- Does the same line work in the `PowerShell` tool?

This file records names and yes/no answers only. No value of a `CLAUDE_*` or `ANTHROPIC_*` variable
is written here.

## Setup

- **Isolation:** as in Q1. Each run had a fresh config and fake home, a stripped child environment
  that keeps `CLAUDE_CODE_CHILD_SESSION`, and the local stub behind `ANTHROPIC_BASE_URL`.
- **Canary:** it passed on each Windows binary. Linux had its own canary in WSL, which also passed.
- **Live state:** the hash of the live `installed_plugins.json` was the same before and after every
  run, on Windows and in WSL.
- **Probe plugin** `spike-q3`: one `SessionStart` handler (`startup`) that prints
  `Q3-SESSION-<session_id>`.
- **Stub:** to each request that carries `q3probe-<uuid>`, it answers with the next command of the
  run's list, as a tool_use of the named shell tool. It cuts the session id from `Q3-SESSION-…` in
  that request, and stops at the end of the list.
- **`dump.sh`** (`dump.ps1` for PowerShell) writes the following to a scratch file, and prints
  `Q3-RAN-<run>`:
  - the working directory;
  - every environment variable name, each with `yes` or `no` for "its value equals the session id
    given as the argument";
  - `yes` or `no` for "`CLAUDE_CONFIG_DIR` is set and equals the scratch config dir".
- **`echo_args.py`** writes its argv to a file.
- **Run:** `claude -p q3probe-<uuid> --model haiku --output-format json --plugin-dir <plugin>
  --allowedTools Bash --debug-file <log>`.
- Scratch: `<temp>/rigger-p2/q/Q3/`.

## Step 2: known-answer control and the permission form

With `--allowedTools Bash`, the stub's tool_use for `sh "<temp>/…/dump.sh" <session id> <run> "<dir>"`
came back as a `tool_result` holding `Q3-RAN-<run>` with `is_error: false`. This held on 2.1.327,
2.1.330 and 2.1.323 (Linux). The first form worked, so `bypassPermissions` and a `permissions.allow`
entry were not needed and not tried.

The session id the stub cut from the request equals the `session_id` of the `-p` result in every
run.

## Answer

- **A stub can script a model-side shell command.** With `--allowedTools Bash`, the tool_use runs and
  its `tool_result` comes back. This held on both Windows binaries and on Linux.
- **`CLAUDE_CONFIG_DIR` reaches the shell process.** A `CLAUDE_CONFIG_DIR` set in the session's
  environment is inherited by the command, unchanged, in the Bash and PowerShell tools.
- **The session id reaches the shell** as `CLAUDE_CODE_SESSION_ID`. This held in both tools on all
  three binaries, and no other variable holds it.
- **The planned `sh "<core root>/bin/py.sh" …` line arrives whole in the Bash tool,** on Windows and
  on Linux.
- **The planned line fails in the PowerShell tool** because `sh` is not found there. That tool runs
  only the form `& "<full path of sh.exe>" …`, which the Bash tool rejects. The PowerShell tool is
  listed only when `CLAUDE_CODE_USE_POWERSHELL_TOOL` is switched on, and the Bash tool is listed in every run.

## Decision

- **The `tool_result` arrived (Step 2, `--allowedTools Bash`):** Task 19 uses that form.
- **`CLAUDE_CONFIG_DIR` reaches the shell process:** the `## Slots` line is
  `sh "<core root>/bin/py.sh" "<core root>/tools/slot-run/slot_run.py" <slot> --session <id> --base <rev>`,
  with no `--config-dir`.
- **The line fails in the PowerShell tool.** The plan's next branch names "the form that arrives whole
  in every shell tool listed". Measured, no such single form exists. The plan's fallback, "No form
  works in PowerShell: the line names the Bash tool", does not literally hold either, because the
  `& "<full sh path>"` form works there. That form needs the machine's path of `sh.exe`. The spike
  does not choose between the following, so the choice for Task 15 goes to the coordinator:
  - (a) the line names the Bash tool: `run with the Bash tool: sh "<core root>/bin/py.sh" …`;
  - (b) a second line for the PowerShell tool with `& "<sh path>"`, where the path comes from
    somewhere not yet measured.

## Departures

- **An extra run** switched on `CLAUDE_CODE_USE_POWERSHELL_TOOL` in the child environment. Without it the
  PowerShell tool is not listed, and Step 4 could not run.
- **A cross-tool run** tried the two full-path forms in both tools, to test the "every shell tool"
  branch.
- **Linux ran** although the argv arrived whole, because the PowerShell half of that branch fired.
  Its result matches Windows.
- **Environment names** other than `CLAUDE_*`, `ANTHROPIC_*` and `HARNESS_*` are given as a count.
  They are the inherited operating-system environment.

## Finding outside the branches

D43 gives `--session` on the command line because "a shell tool process may not know" its session.
Measured, it does know it through `CLAUDE_CODE_SESSION_ID`, on every binary and in both tools.
Nothing in the plan is changed here.
