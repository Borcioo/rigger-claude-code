## A. JS/TS

### 1. oxlint (oxc-project)
- **Version:** oxlint 1.89.0, published 2026-10-19 [npm: https://registry.npmjs.org/oxlint ; https://github.com/oxc-project/oxc/releases]. Weekly release cadence (1.86.0 2026-09-28, 1.87.0 10-05, 1.88.0 10-13, 1.89.0 10-19) [gh-rel oxc-project/oxc]. Node `^20.19.0 || >=22.12.0` [npm oxlint 1.89.0].
- **Rule coverage:** 871 built-in rules, 111 on by default, 334 with fixes (oxlint 1.89-era docs, https://oxc.rs/docs/guide/usage/linter/rules.html). Plugin groups on the rules page: eslint, typescript, import, jest, vitest, jsdoc, jsx-a11y, nextjs, node, oxc, promise, react, react-perf, unicorn, vue. react-hooks rules (`exhaustive-deps`, `hooks`) live under the `react` plugin (same page). Linter overview names ESLint core, TypeScript, React, Jest, Vitest, Import, Unicorn, jsx-a11y (https://oxc.rs/docs/guide/usage/linter.html). Vue rules exist natively (listed in rules page and in 1.89.0 release notes making Vue 3 rules "recommended").
- **Framework files:** lints only `<script>` blocks of `.vue`, `.svelte`, `.astro`; "No template linting yet" for Vue, Svelte, Angular, Astro, Nuxt (https://oxc.rs/compatibility ; https://oxc.rs/docs/guide/usage/linter.html).
- **Type-aware linting:** runs through `oxlint-tsgolint` (Go, on typescript-go). Requires `oxlint-tsgolint` and **TypeScript 7.0 or later**; 59 of 61 typescript-eslint type-aware rules supported; enable via `--type-aware` or `options.typeAware: true` in root config; some legacy tsconfig options (e.g. `baseUrl`) unsupported; monorepo deps must be built so `.d.ts` exist; large repos may use lots of memory (https://oxc.rs/docs/guide/usage/linter/type-aware.html, undated page, © 2026). oxlint 1.89.0 declares peer `oxlint-tsgolint >=7.0.2003`; latest tsgolint 7.0.2004 (2026-10-10) [npm]. Status label: the docs page and feature list give no alpha/beta/stable label for type-aware (feature list marks only JS plugins "alpha"); a search-engine summary claimed "stable" but I could not confirm that on the primary page -> treat label as **unconfirmed**. Type-aware alpha announcement: https://oxc.rs/blog/2025-12-08-type-aware-alpha.html (Dec 2025). Docs say type-check diagnostics can replace a separate `tsc --noEmit` in CI (same type-aware page).
- **Running ESLint JS plugins (`jsPlugins`):** status **alpha** (https://oxc.rs/docs/guide/usage/linter/js-plugins.html; feature list line "JS plugins (alpha)"). Configure via `jsPlugins` array in `.oxlintrc.json`/`oxlint.config.ts`, rules as `plugin/rule`; aliasing with `{name, specifier}`. Supported: AST traversal, fixes, options, selectors, SourceCode + token APIs, scope analysis, code path analysis, inline disables, LSP. Not supported: custom parsers/file formats (Svelte, Vue, Angular), rules needing TS type info (custom type-aware JS rules). ESLint APIs removed in ESLint v9 or earlier mostly not implemented (older plugins that call `context.getScope()` fail; workaround package `oxlint-compat-wrapper`) (https://github.com/oxc-project/oxc/discussions/20245). Conformance-tested plugins: eslint-plugin-react-hooks, @stylistic, testing-library, sonarjs, @e18e, storybook, playwright, cypress, regexp, mocha (docs page + https://github.com/oxc-project/oxc/tree/main/apps/oxlint/conformance/snapshots). Community-reported working in discussion #20245 (updated 2026-10-16): @angular-eslint 22.6.0, eslint-plugin-tailwindcss 4.4.0, eslint-plugin-boundaries 7.2.0 on Oxlint 1.88.0.
- **@wordpress/eslint-plugin under oxlint: UNCONFIRMED.** Not in the docs' known-working list, not in the conformance suite, no mention in discussion #20245 (28 comments), and no issue in oxc-project/oxc or WordPress/gutenberg mentions both (`gh search issues`, 2026-10-20). Facts that bear on feasibility: @wordpress/eslint-plugin 27.1.0 (2026-10-07) is flat-config, peers `eslint ^9 || ^10`, `prettier >=3`, `typescript >=5` and depends on typescript-eslint, eslint-plugin-import, jsx-a11y, react, react-hooks 7, jsdoc, jest, @vitest/eslint-plugin, playwright, eslint-plugin-prettier [npm https://registry.npmjs.org/@wordpress/eslint-plugin/27.1.0]; its own rules are `@wordpress/no-unsafe-wp-apis`, `dependency-group`, `i18n-*`, `valid-sprintf`, etc. (https://github.com/WordPress/gutenberg/blob/trunk/packages/eslint-plugin/README.md). Plain-JS custom rules (i18n-*, valid-sprintf) are the most likely to run as jsPlugins; the recommended preset relies on `eslint-plugin-prettier` (runs Prettier inside ESLint), which is the opposite of what you want with oxlint. Must be tried in a spike.
- **Official ESLint -> oxlint migration:** `npx @oxlint/migrate [eslint.config.js path]` (v1.89.0, 2026-10-19 [npm]); reads ESLint v9/v10 flat config, writes `.oxlintrc.json`, keeps severities/options/overrides/globals/ignores, migrates plugins as JS plugins by default (`--js-plugins=false` to skip), `--type-aware` flag adds type-aware rules. Does not convert eslintrc v8 (use `@eslint/migrate-config` first) nor local custom plugins (add to `jsPlugins` by hand) (https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint.html). Companion: `eslint-plugin-oxlint` to turn off overlapping ESLint rules when running both.
- **Measured speed claims:** docs: "50 to 100 times faster than ESLint" (https://oxc.rs/docs/guide/usage/linter.html; benchmark repo oxc-project/bench-linter). JS plugins: Node.js repo, 6,298 files, 104 Rust rules + 75 JS-plugin rules + 23 custom: ESLint 1m43s vs Oxlint 21s = 4.8x; FAQ range 4x-100x (https://oxc.rs/blog/2026-03-11-oxlint-js-plugins-alpha, March 2026). That post also says Windows users reported problems incl. out-of-memory with JS plugins and recommends WSL (March 2026; may be outdated) - relevant on a Windows dev box.

### 2. oxfmt
- **Version/status:** oxfmt 0.74.0, 2026-10-19 [npm]. **Beta** since 2026-02-24 ("now passes 100% of Prettier's JavaScript and TypeScript conformance tests"; roadmap to stable: Prettier plugin support, xxx-in-js formatting, stability, performance; no timeline) (https://oxc.rs/blog/2026-02-24-oxfmt-beta). Still 0.x; no stable/GA announcement as of 2026-10-20. XML/SVG listed as "Planned for Oxfmt 1.0" (https://oxc.rs/compatibility).
- **Prettier compatibility:** "compatible with Prettier v3.9.9 for many configurations"; may intentionally diverge where Prettier looks like a bug; Prettier plugins **not supported** except built-in equivalents (tailwindcss, svelte, astro, packagejson); default `printWidth` is 100 (migration sets 80) (https://oxc.rs/docs/guide/usage/formatter/migrate-from-prettier.html). Migration: `npm add -D oxfmt@latest && npx oxfmt --migrate=prettier && npx oxfmt` (same page). Prettier config formats YAML/JSON5/TOML not accepted.
- **Languages:** JS, JSX, TS, TSX, JSON/JSONC/JSON5, YAML, TOML, HTML, Angular, Vue, Svelte, CSS/SCSS/Less, Markdown, MDX, GraphQL, Ember, Handlebars (https://oxc.rs/docs/guide/usage/formatter.html); Astro supported (oxfmt 0.73.0 release note "Astro support", needs `@astrojs/compiler-rs` installed per https://oxc.rs/compatibility). Built-in import sorting, Tailwind class sorting, package.json sorting. Speed: "30x faster than Prettier and 3x faster than Biome on an initial run without caching" (beta post); formatter page says ~2x faster than Biome (inconsistent between pages).
- **wp-prettier style (spaces inside parentheses): NO.** The full config reference lists no `parenSpacing`/`spaceInParens`/array-bracket-space option; only `bracketSpacing` for object literals (https://oxc.rs/docs/guide/usage/formatter/config-file-reference.html). Prettier plugins/forks are not loadable, so wp-prettier output cannot be reproduced. Context: `@wordpress/prettier-config` 4.57.0 enables `parenSpacing: true` only when the installed Prettier is the `wp-prettier` fork (source: https://github.com/WordPress/gutenberg/blob/trunk/packages/prettier-config/lib/index.js); `@wordpress/scripts` 36.1.0 depends on `prettier: npm:wp-prettier@^3.9.6` [npm]; wp-prettier latest 3.9.6, 2026-09-14 [npm https://registry.npmjs.org/wp-prettier].
- Gutenberg maintainer position (2026-06-22): for lint/format/test tools "developers should be using these tools directly instead of using an abstraction layer"; the issue proposing replacing ESLint+Prettier in @wordpress/scripts with Oxc/Biome is open, no decision (https://github.com/WordPress/gutenberg/issues/78836).

### 3. Biome 2.x
- **Version:** @biomejs/biome 2.5.15, 2026-09-30 [npm; gh-rel biomejs/biome]. 2.5.x patch cadence ~weekly/biweekly (2.5.10 08-21 ... 2.5.15 09-30). v2.5 minor released 2026-06-05; v2.4 2026-02-10 (https://biomejs.dev/blog/). No Biome 3 information found on the blog/roadmap pages fetched (unconfirmed whether planned).
- **Migrate commands:** `biome migrate eslint --write` (ports rules, globals, overrides, ignores; supports legacy + flat configs, extends, shared/plugin configs, `.eslintignore`; `--include-inspired` also migrates "inspired by" rules; plugin rules must be configured by hand; sets rule preset to none) and `biome migrate prettier --write` (writes every option explicitly because Biome defaults differ) (https://biomejs.dev/guides/migrate-eslint-prettier/, examples reference schema 2.5.15).
- **Prettier parity:** no percentage given on the differences page; lists intentional divergences (property unquoting, a few TS edge cases, stricter parser) (https://biomejs.dev/formatter/differences-with-prettier/).
- **Space-inside-parens option (new, relevant for WP JS style):** `formatter.delimiterSpacing` (boolean, default false) added in Biome 2.5; implemented for JavaScript/TypeScript, CSS, JSON, GraphQL. In JS it produces `function name( param )` and `[ 1, 3, 4 ]`; applies to parens, square brackets, template interpolations, TS angle brackets and JSX expression braces (https://biomejs.dev/blog/biome-v2-5/ ; https://biomejs.dev/reference/configuration/). The release post does not mention WordPress; **exact equivalence with wp-prettier `parenSpacing` output is unconfirmed** - needs a diff test on a real WP codebase (also Biome `indentStyle` default is tab, `lineWidth` 80).
- **GritQL plugins:** supported; match patterns, report diagnostics via `register_diagnostic()`, and (since 2.5) suggest code fixes with `=>` and `fix_kind = "safe"|"unsafe"` (default unsafe); target languages JS, CSS, JSON only; configured as `"plugins": ["./x.grit"]` with optional `includes` globs; no JS plugins (https://biomejs.dev/linter/plugins/ ; v2.5 post). GritQL accepted into the Biome org 2025-12-18 (blog).
- **Vue/Svelte/Astro:** all three **experimental** (parse/format/lint = "Experimental" in the language table), supported since v2.3.0, improved in 2.4/2.5; "Biome can format and lint the HTML, CSS and JavaScript parts" with possible false positives for embedded-language lint rules (https://biomejs.dev/internals/language-support/). Plugins (GritQL) not available for HTML/Vue/Svelte/Astro. SCSS, YAML, Markdown not supported (in progress / not started).
- Other: 2.5 passed 500 lint rules; type-aware rules use Biome's own inference (not tsc) with a watch mode; first cross-file CSS-class rules (nursery) (v2.5 post).

### 4. TypeScript 7 (native)
- **Status: released and stable.** `typescript@7.0.2` is npm `latest` (published 2026-07-08 [npm]); announcement dated 2026-07-08 (https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/); GitHub release page marks TypeScript 7.0.2 "Latest" but shows the date 20 Aug 2026 (reason for the date difference not stated; npm `time` used as the publish date) (https://github.com/microsoft/TypeScript/releases). TS 6.0 (last JS-based release) was 6.0.2 on 2026-03-23 and 6.0.3 on 2026-04-16 (same page). `typescript@next` is 7.1.0-dev.20261019.1 (2026-10-19 [npm]). microsoft/typescript-go repo archived/merged into microsoft/TypeScript (https://github.com/microsoft/typescript-go).
- **No programmatic API in 7.0.** "TypeScript 7.0 does not ship with an API. We expect TypeScript 7.1 to ship with a new (and different) API"; no 7.1 date given, feature releases "every 3-4 months" (announcement). `require("typescript")` exposes only `version`/`versionMajorMinor`, and `typescript/lib/tsc` is not exported (typescript-eslint#12518, vuejs/language-tools#6124).
- **Speed claims:** 8x-12x faster full builds; vscode 125.7s -> 10.6s, sentry 139.8s -> 15.7s, bluesky 24.3s -> 2.8s, playwright 12.8s -> 1.47s (announcement).
- **Defaults/removals to check before upgrading:** `strict` true; `types` defaults to `[]`; `rootDir` defaults to `./`; `module` esnext; removed `target: es5`, `moduleResolution node/node10/classic`, `baseUrl`, `module amd/umd/systemjs/none`, `esModuleInterop:false`; CLI file args ignored when tsconfig.json exists unless `--ignoreConfig` (announcement). Also oxlint type-aware needs TS >= 7.
- **Supported way to keep TS 6 for API consumers:** package `@typescript/typescript6` (re-exports TS 6 API, provides `tsc6`). Two official recipes: (a) only TS 6 under the `typescript` name: `npm install -D typescript@npm:@typescript/typescript6`; (b) both: devDependencies `"@typescript/native": "npm:typescript@^7.0.2"` and `"typescript": "npm:@typescript/typescript6@^6.0.2"` (npm aliases; the post does not discuss npm `overrides`) (announcement, section "Running side-by-side with TypeScript 6.0"). Note `typescript-eslint` 8.72.0 itself now has a dependency alias `@typescript/native -> npm:typescript@^7.0.2` [npm], consistent with that recipe (purpose unconfirmed).
- **Tool compatibility (all verified 2026-10-20):**
  - **typescript-eslint:** 8.72.0 (2026-10-19), peer `typescript >=4.8.4 <6.1.0` [npm]. Not compatible with TS 7; maintainer: "there is no TS 7 API at this time ... set up typescript-eslint to use TS 6" (https://github.com/typescript-eslint/typescript-eslint/issues/12518, closed). Tracking: https://github.com/typescript-eslint/typescript-eslint/issues/10940 (open, updated 2026-09-29); draft prototype of TS 7.1 native backend: PR #12803 (not merged as of the search). Alternative: oxlint+tsgolint for type-aware rules (needs TS 7).
  - **vue-tsc:** 3.3.13 (2026-10-10), peer `typescript >=5.0.0` [npm], but crashes with TS 7 (`ERR_PACKAGE_PATH_NOT_EXPORTED ./lib/tsc`) (https://github.com/vuejs/language-tools/issues/6124). Maintainer status (2026-07-12/07-23): all published packages need the TS 6 JS API; TS 7.1 support is on the roadmap via "content mappers" (microsoft/typescript-go#4712, design validation) and vue-tsc would then be deprecated; interim: `typescript-native-bridge` override (~2.7x faster, 12.8s -> 4.7s) or community vue-tsgo/Golar; native SFC pipeline explicitly out of scope (https://github.com/vuejs/language-tools/issues/5381, closed 2026-08-07; PR #6170 draft). Net: keep TS 6 for vue-tsc.
  - **@astrojs/check:** 0.9.11 (2026-10-19), peer `typescript ^5.0.0 || ^6.0.0` [npm]. Astro issue #17268 (closed 2026-09-17) fixed the "typescript not installed" detection with TS 7 in `astro` core/@astrojs/check, but the TS 7 announcement says Astro/Vue/MDX/Svelte projects "will need to continue using TypeScript 6.0 for now" (https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#typescript-and-embedded-languages). Astro 7.4.1 itself depends on `typescript ^6.0.3` [npm]. Net: keep TS 6 under the `typescript` name for `astro check`.
  - **tsx:** 4.23.15 (2026-09-20) has no typescript dependency/peer (esbuild-based transpile) [npm] -> unaffected by TS 7 (no type checking). **ts-node:** 10.9.2 last release 2023-12-08, repo last push 2024-07-18, peer `typescript >=2.7`, needs the JS API [gh-rel TypeStrong/ts-node] -> will not work with TS 7; no maintainer statement as of 2026-10-20 (unconfirmed); migrate to tsx / Node type stripping.
  - **Vitest typecheck:** Vitest 5.0.5 runs `tsc --noEmit` or `vue-tsc --noEmit` under the hood (https://vitest.dev/guide/testing-types); docs do not mention TS 7/tsgo. Plain `tsc` = TS 7 should work as a CLI (inference from docs; not verified), `vue-tsc` needs TS 6.
  - **Practical setup:** `typescript` -> `@typescript/typescript6` alias (for typescript-eslint, vue-tsc, astro check, Volar) + `@typescript/native` (TS 7) for fast `tsc` CI type-checking of plain TS packages.

### 5. knip
- **Version:** knip 6.42.1, 2026-10-19 [npm]. v6 announced 2026-03-20: replaced the TypeScript backend with `oxc-parser` + `oxc-resolver` (single-pass parse, no TS program), 2-4x faster than v5.88.0 (sentry 11.0s -> 4.0s, astro 4.0s -> 2.0s); Node >= 20.19.0; removed `classMembers` issue type (relied on the TS language service `findReferences`, uncertain under TS 7) (https://knip.dev/blog/knip-v6). npm metadata for 6.42.1 lists no peerDependencies and `typescript 7.0.2` only as devDependency, while the getting-started page still says to install `typescript` and `@types/node` (docs/metadata discrepancy) [npm; https://knip.dev/overview/getting-started].
- **What it finds:** unused files, dependencies/devDependencies, optional peer deps referenced, unlisted deps and binaries, unused/unresolved catalog entries, unresolved imports, unused exports and exported types (also enum/namespace members, exports in used namespaces), duplicate exports, circular dependencies (`cycles`); auto-fix (`--fix`) for files, dependencies, catalog, exports, types, enum/namespace members (https://knip.dev/reference/issue-types).
- **Monorepo:** any directory with `package.json` is a workspace; detected from `workspaces` in package.json, `pnpm-workspace.yaml`, or `workspaces` object in knip config; per-workspace `entry`/`project`/`ignore*`/plugin config; `--workspace/-W` filter pulls in ancestor, dependency and dependent workspaces; `--isolate-workspaces` default since v6 (https://knip.dev/features/monorepos-and-workspaces ; v6 post).
- **Plugins:** 195 plugins; present for Vite, Vitest, Astro (+Astro DB, Markdoc, astro-og-canvas), Playwright, `laravel-vite-plugin`, Vue, ESLint, Oxlint, Biome, TypeScript, Tailwind, Prettier, husky, lint-staged, webpack. **No** Inertia plugin and **no** `@wordpress/scripts` plugin (https://knip.dev/reference/plugins). Config files: `knip.json(c)`, `.knip.json(c)`, `knip.ts/js`, `knip.config.*`, or `package.json` `"knip"` key (https://knip.dev/overview/configuration).
- **How it is run:** CLI `knip`; exit 0 clean, 1 issues found, 2 failure to run; `--max-issues`, `--no-exit-code`, `--production`, `--strict`, `--cache` (10-40% faster consecutive runs; known stale-cache limitation), reporters `symbols|compact|json|sarif|markdown` (https://knip.dev/reference/cli). The docs I fetched do not prescribe CI-vs-periodic; with exit code 1 on any finding it is CI-gate-capable but needs per-workspace entry config to avoid false positives. My recommendation (not a source claim): PR gate only in repos where it is baseline-clean, otherwise scheduled run or `--include` subset.

### 6. ast-grep
- **Version:** @ast-grep/cli 0.51.0, 2026-10-15 [npm; gh-rel ast-grep/ast-grep: 0.50.0 2026-10-09]. Still 0.x. Since 0.50.0, native custom-language parsers in `customLanguages` need explicit permission/saved project trust (https://ast-grep.github.io/guide/project/project-config.html).
- **Rule definition:** project = `sgconfig.yml` (keys `ruleDirs`, `testConfigs`, `utilDirs`, `customLanguages`, `languageGlobs`) + rule YAML files under the rule dirs; `ast-grep new` scaffolds `rules/`, `rule-tests/`, `utils/`, `sgconfig.yml`. Rule YAML core fields `id`, `message`, `severity` (error|warning|hint|info|off), `language`, `rule` (e.g. `pattern: eval($CODE)`), optional `fix`, `note`, `utils`; run with `ast-grep scan` (https://ast-grep.github.io/guide/scan-project.html). Tests: `testConfigs: [{testDir: rule-tests}]`, YAML with `valid`/`invalid` code, snapshots, `ast-grep test`, `--update-all`, `--interactive` (https://ast-grep.github.io/guide/test-rule.html). Rule scans without project config possible via `--rule`/`--inline-rules`.
- **CI:** `ast-grep scan --format github|sarif`, `--json[=pretty|stream|compact]`; exit code 1 when at least one error-severity rule matches (https://raw.githubusercontent.com/ast-grep/ast-grep.github.io/main/website/reference/cli/scan.md). Official GitHub Action `ast-grep/action` (inputs `version`, `config`, `paths`) (https://github.com/ast-grep/action, pushed 2026-10-10).
- **PHP:** built-in language `php` (extension `.php`) using `tree-sitter-php 0.24.0` (https://ast-grep.github.io/reference/languages.html ; https://github.com/ast-grep/ast-grep/blob/main/crates/language/Cargo.toml). Other built-ins include TypeScript/TSX/JS/HTML/CSS/YAML/JSON/Markdown; no first-class Vue/Astro/Blade language in the list (unconfirmed whether HTML language injection covers them).

### 7. Mago (carthage-software/mago)
- **Version:** 1.58.2, 2026-10-19 [pkg carthage-software/mago; https://github.com/carthage-software/mago/releases]. 1.0.0 shipped 2025-12-20 (GitHub releases). Very fast cadence (1.57.0 on 10-14, three releases on 10-19). Dual MIT/Apache-2.0, single Rust binary; Windows binaries (`x86_64-pc-windows-msvc.zip`) published; also installable via Composer, Homebrew, Cargo, Docker (https://github.com/carthage-software/mago/blob/main/docs/content/en/guide/installation.md). Composer wrapper pins a matching binary; PHP constraint `~8.1 ... ~8.6` for the wrapper [pkg].
- **Four tools in one binary:** formatter, linter, static analyzer, architectural guard; config `mago.toml`; commands `mago format|lint|analyze|guard` (https://github.com/carthage-software/mago/blob/main/docs/content/en/tools/overview.md).
- **Formatter:** parse-and-reprint (Prettier/rustfmt style); **PER-CS default**; presets `default` (PER-CS), `psr-12`, `laravel` ("Laravel Pint's `laravel` preset"), `drupal`; options can override the preset (https://github.com/carthage-software/mago/blob/main/docs/content/en/tools/formatter/configuration-reference.md). Byte-for-byte equality with Pint output is **unconfirmed** (docs only say it is Pint's preset). **No WordPress preset.** Only spacing knob of WP flavour: `space-within-grouping-parenthesis` (`( 1 + 2 )`), default false - there is no option for spaces inside call/definition parens, so WPCS formatting cannot be reproduced (same doc).
- **Linter:** 190 rules in 9 categories (rules page, https://github.com/carthage-software/mago/blob/main/docs/content/en/tools/linter/rules.md), auto-fixes, plus framework "integrations" enabled in `[linter].integrations` (https://github.com/carthage-software/mago/blob/main/docs/content/en/tools/linter/integrations.md). Integration rules that actually exist: **Laravel 10** (e.g. `no-request-all`, `no-implicit-model-query`, `prefer-casts-method`, `middleware-in-routes`, `prefer-anonymous-migration`, `final-controller`), **WordPress 8** (`no-unescaped-output`, `nonce-verification`, `prepared-sql`, `validated-sanitized-input`, `no-direct-db-query`, `use-wp-functions`, `no-db-schema-change`, `no-roles-as-capabilities`), PHPUnit 4, Pest 4, Symfony 4, Psl 9; Drupal/Magento/Doctrine etc. listed but "some of these are placeholders for future rules". The 8 WP rules are a small, security-flavoured subset - nowhere near WPCS's sniff set (WPCS 3.4.x; compare counts: unconfirmed).
- **Analyzer:** whole-project type analysis, understands Psalm and PHPStan annotations, generics, conditional types, flow narrowing, "runs an entire project in seconds" (https://github.com/carthage-software/mago/blob/main/docs/content/en/tools/analyzer/overview.md). Baseline support documented (docs/content/en/fundamentals/baseline.md). **No stated maturity/stability level and no stated feature comparison with PHPStan/Psalm** in the docs I read; the only comparative statements are speed/memory: benchmark dashboard (https://carthage-software.github.io/php-toolchain-benchmarks/) and "around 3.5x less memory than Psalm" (https://github.com/carthage-software/mago/blob/main/docs/content/en/benchmarks.md). It does **not** load PHPStan extensions (Larastan, phpstan-wordpress): Mago has its own extension system (external worker processes, first-party PHP SDK; linter rules + analyzer plugins; formatter/guard have no extension API) (https://github.com/carthage-software/mago/blob/main/docs/content/en/extensions/overview.md). Community extensions exist but are tiny: `laramago/laramago` (1.8k installs), `rlorenzo/mago-wordpress` ("WPCS-equivalent linter rules", 33 installs), `amateescu/mago-drupal` (Packagist search 2026-10-20) -> treat as unvetted.

PHPUnit 13 result cache is on by default (`--order-by=defects`, `--stop-on-defect`); PCOV = line coverage only, Xdebug = branch/path; no primary-source speed comparison found. Pest `--parallel` docs say use WSL on Windows.
8. **WordPress sniffs are stuck on PHPCS 3**: PHPCS 4.0.4 exists, WPCS 3.4.1 (requires `^3.13.5`; also a security release - arbitrary command execution on untrusted code with WordPress/WordPress-Extra) and PHPCompatibilityWP (stable 2.1.8; 3.0 alpha) do not support PHPCS 4; WP core itself pins PHPCS 3.13.5. `phpcs --parallel` needs pcntl, which does not exist on Windows PHP (use `--cache`, or WSL/CI).
9. **WP integration tests are capped at PHPUnit <= 9.6** (core uses polyfills ^1.1; wp-test-utils 1.2.1 supports PHPUnit 5.7-9; WP_Mock 1.1.1 hard-requires ^9.6; wp-browser 4.7.2 requires `<12`); status of core's PHPUnit 10+/12 work (Trac #62004) unconfirmed. Brain Monkey 2.7.0 has no PHPUnit dependency (PHPUnit 10+ use untested by project). No official parallel story: ParaTest's `TEST_TOKEN` per-process DB is plausible but unverified and current ParaTest needs PHPUnit 11-13; wp-browser has an `@internal` `parallel-run --workers=auto`; wp-env supports parallel *environments* via `--config`.
10. **Docker-free WP integration tests**: wp-env's Playground runtime has no `wp-env run` (cannot run PHPUnit); `@wp-playground/cli php` runs plugin PHPUnit (documented), but `WP_UnitTestCase` needs the `WP_TESTS_SKIP_INSTALL=1` workaround (issue #3783 open) and runs on SQLite. **szepeviktor/phpstan-wordpress** (v2.0.4) carries an "abandonment" notice; stubs are current (php-stubs/wordpress-stubs v7.1.2).
